# Milestone 1: HTTP/1.1 Fundamentals & Minimal Server

## 1. Thí nghiệm Server tối thiểu và quan sát bằng curl (`lab/hello.js`)

### Mục tiêu:
Hiểu rõ bản chất của HTTP/1.1: **chỉ là text thuần truyền qua socket TCP**. Quan sát cách Node.js tự động quản lý các header (`Date`, `Connection`, `Content-Length`, `Transfer-Encoding`) dựa trên cách gọi `res.write()` và `res.end()`.

---

### Dự đoán trước khi chạy & Câu hỏi đặt ra:
1. **Response có những header nào mà bạn không hề đặt?**
2. **Có `Content-Length` không? Có `Transfer-Encoding: chunked` không?**
3. **Sửa handler thành `res.write('a'); res.end('b');` thì 2 câu trên thay đổi ra sao?**
4. **Gọi `curl -v` hai lần liên tiếp, dòng `Connection: keep-alive` và `Keep-Alive: timeout=...` nghĩa là gì?**

### Phân tích & Trả lời chi tiết:

| Câu hỏi | Quan sát thực tế | Giải thích cơ chế bên dưới (Node.js & HTTP/1.1) |
|---|---|---|
| **1. Header nào tự động xuất hiện mà ta không hề đặt?** | `Date`, `Connection`, `Keep-Alive`, (`Content-Length` hoặc `Transfer-Encoding`) | Node.js HTTP runtime tự động tuân thủ RFC 9112 / RFC 7230:<br>- `Date`: Thời gian GMT sinh response.<br>- `Connection: keep-alive`: Mặc định giữ kết nối TCP mở cho HTTP/1.1.<br>- `Keep-Alive: timeout=5`: Báo cho client biết sau 5 giây không gửi thêm request thì server sẽ ngắt kết nối.<br>- `Content-Length` hoặc `Transfer-Encoding`: Bắt buộc phải có một trong hai để client biết điểm kết thúc của body. |
| **2. Case `res.end('hello')`: Có `Content-Length` hay `Transfer-Encoding`?** | **Có `Content-Length: 5`**<br>Không có `Transfer-Encoding: chunked` | Khi gọi trực tiếp `res.end('hello')`, Node.js chưa gửi header nào ra socket. Tại thời điểm `end()`, Node biết trước toàn bộ độ dài nội dung (5 bytes chuỗi ASCII `'hello'`), nên nó tự tính toán và gắn header `Content-Length: 5` trước khi flush toàn bộ response ra TCP socket. |
| **3. Case `res.write('a'); res.end('b')`: Thay đổi ra sao?** | **Mất `Content-Length`**<br>Xuất hiện **`Transfer-Encoding: chunked`** | Khi `res.write('a')` được gọi, Node.js bắt buộc phải gửi HTTP Headers (`HTTP/1.1 200 OK...`) ngay lập tức để kịp truyền chunk `'a'`. Tại thời điểm này, Node **chưa thể biết** trong tương lai bạn còn gọi thêm bao nhiêu lần `write()` hay gửi tổng cộng bao nhiêu bytes. Vì vậy, Node không thể đặt `Content-Length`. Để không phải đóng kết nối TCP mà client vẫn biết khi nào body kết thúc, HTTP/1.1 quy định dùng **chunked transfer encoding** (gửi từng chunk kèm độ dài hex và kết thúc bằng chunk rỗng 0-byte). |
| **4. `Connection: keep-alive` & `Keep-Alive: timeout=5` nghĩa là gì?** | Tái sử dụng kết nối TCP hiện có trong tối đa 5 giây | - **`Connection: keep-alive`**: Sau khi nhận xong response, socket TCP vẫn mở (`left intact`), client có thể gửi ngay request tiếp theo trên socket đó mà không cần bắt tay 3 bước (TCP 3-way handshake SYN-SYNACK-ACK) lại từ đầu, giảm đáng kể latency.<br>- **`Keep-Alive: timeout=5`**: Server Node.js (mặc định `server.keepAliveTimeout = 5000ms`) thông báo sẽ giữ socket mở tối đa 5 giây nếu không có request mới. Quá 5 giây idle, server sẽ chủ động đóng (FIN/RST) để tránh cạn kiệt socket descriptor. |

---

### Đúc kết cốt lõi:
1. **HTTP/1.1 chỉ là text có định dạng truyền trên dòng stream TCP byte-level**.
2. Khi streaming (`res.write()`), ta gửi dữ liệu từng đợt mà không biết trước tổng kích thước -> Bắt buộc dùng `Transfer-Encoding: chunked`.
3. Khi gửi một lần (`res.end(data)`), Node biết tổng kích thước -> Tự động thêm `Content-Length: <size>`.
4. Cơ chế Keep-Alive giúp tiết kiệm chi phí thiết lập kết nối TCP, nhưng cần timeout để tránh rò rỉ tài nguyên.

## 2. createApp và HTTP Server chuẩn hóa (`src/core/app.js`)

### Bản ngây thơ ban đầu (và vấn đề của nó):

**Route `/echo` ban đầu:**
```js
const chunks = [];
for await (const chunk of req) chunks.push(chunk);
const body = Buffer.concat(chunks);
res.end(body);
```

**Tại sao hỏng:** Nếu client gửi 500MB body, toàn bộ 500MB nằm trên V8 heap. 10 client đồng thời = ~5GB RAM → OS OOM Killer giết process.

**Số liệu chứng minh:** Benchmark BREAK #1 cho thấy khi không có giới hạn, server chấp nhận bất kỳ payload size nào mà không có cơ chế kiểm soát.

### Giải pháp (hai lớp phòng thủ):
1. **Vòng ngoài (Header):** Kiểm tra `Content-Length` header trước khi đọc stream → từ chối 413 ngay lập tức.
2. **Vòng trong (Stream):** Đếm byte tích lũy trong `for await` → ngừng đọc khi vượt ngưỡng.

**Trade-off:** Cần gọi `req.resume()` sau khi trả 413 để xả bỏ dữ liệu thừa. Nếu dùng `req.destroy()` ngay, client nhận `ECONNRESET` thay vì thấy 413 vì TCP RST xóa sạch read buffer.

## 3. BREAK #2 — Slowloris Attack và Timeout Protection

### Bản ngây thơ (và vấn đề):
Server không có `headersTimeout`. Kẻ tấn công mở 1000 socket TCP, nhỏ giọt 1 byte header mỗi 30 giây → server giữ 1000 kết nối mở mãi mãi → cạn kiệt File Descriptors.

### Giải pháp:
```js
server.headersTimeout = 5000;   // Chờ client gửi xong headers tối đa 5s
server.requestTimeout = 10000;  // Toàn bộ request (kể cả body) tối đa 10s
server.keepAliveTimeout = 5000; // Idle connection sống tối đa 5s
```

### Điều bất ngờ - `connectionsCheckingInterval`:
Khi đặt `headersTimeout=5000`, thực tế server đóng socket sau **~30 giây** thay vì 5 giây. Lý do: Node.js dùng `server.connectionsCheckingInterval` (mặc định **30_000ms**) để định kỳ quét các socket timeout, thay vì chạy timer riêng cho từng kết nối (vì timer riêng cho 10,000 connection sẽ gây overhead lớn).

Kết quả quan sát từ `lab/slowloris.js`: Server gửi `HTTP/1.1 408 Request Timeout` và đóng socket sau khoảng ~30 lần nhỏ giọt (30 giây).

## 4. BREAK #3 — Event Loop Blocking

### Quan sát thực tế:
```
[4] Thời gian chờ của /health: 2796.29 ms
    (dù /health chỉ là hàm trả về text tĩnh!)
```

### Giải thích cơ chế:
1. Node.js chạy JavaScript trên **một thread duy nhất** (Call Stack).
2. Route `/block` dùng `while (Date.now() < end) {}` chiếm Call Stack liên tục 3 giây, CPU lên 100%.
3. Event Loop không thể quay về **Poll Phase** để đọc I/O mới từ socket `/health`.
4. Request `/health` phải xếp hàng chờ tại OS kernel queue cho đến khi Call Stack rỗng.

### Số liệu từ Event Loop Monitor:
```
Bình thường: p50=15.58ms  p99=16.61ms  maxMs=16.91ms
Sau /block:  p50=15.55ms  p99=17.81ms  maxMs=3011.51ms  ← nhảy vọt 178 lần!
```

## 5. Graceful Shutdown

### Cấu trúc (`bin/server.js`):
```
SIGTERM/SIGINT
    │ (guard: chỉ chạy một lần)
    ▼
server.closeIdleConnections()   // đóng keep-alive rảnh ngay
    │
    ▼
server.close(callback)          // ngừng nhận connection mới, chờ in-flight xong
    │
    ├── Thành công → process.exit(0)
    │
    └── Timeout 10s → server.closeAllConnections() → process.exit(1)
```

**Tại sao cần `closeIdleConnections()`:** Nếu chỉ gọi `server.close()`, các keep-alive socket rảnh (không có request đang chạy) vẫn giữ server sống mãi cho đến khi hết `keepAliveTimeout`. Với `keepAliveTimeout=5s` và benchmark traffic cao, có thể có hàng trăm idle connections → server không thoát được.

## Điều bất ngờ nhất

1. **Access log tốn -20% throughput** — logging tưởng "miễn phí" nhưng không phải.
2. **c=10 latency p99 = 3ms vs c=100 = 36ms** — throughput tương đương nhưng latency khác nhau 12 lần. Đây là sự khác biệt giữa *throughput* và *user-perceived latency*.
3. **`connectionsCheckingInterval` = 30s** — timeout không tức thì như bạn nghĩ; Node quét định kỳ.
4. **Event loop maxMs nhảy từ 17ms lên 3011ms** — monitor cho thấy con số rõ ràng thay vì "cảm giác chậm".
