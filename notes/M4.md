# M4 - User Store

## Memory store interface

`createMemoryUserStore()` implements an async `create`, `findByEmail`, and
`findById` interface. Keeping these methods async means auth handlers do not
need to change when M9 replaces the in-memory implementation with a Postgres
repository.

## Decisions

1. **Normalize email in the store.** The store is the uniqueness boundary, so
   every caller gets the same trim/lowercase behavior. If both handler and store
   normalize independently with rules that later drift, registration and lookup
   could disagree about which account an address identifies. The stored email
   is canonicalized to lowercase and trimmed.
2. **Use `DuplicateEmailError`, not `HttpError`.** Duplicate email is a domain
   condition, while HTTP status and response formatting belong to the handler
   or transport layer. Keeping HTTP types out of storage lets other callers use
   the same store without depending on HTTP.
3. **Check and insert without an `await` between them.** An async function runs
   synchronously until its first `await`. Checking the normalized key and
   immediately writing both maps in that uninterrupted section prevents two
   concurrent create calls from both passing the duplicate check. The public
   method remains async; persistence can be swapped later for a database with
   a unique constraint and transaction.

The store returns copies of user records so callers cannot mutate internal map
state. `createdAt` is a `Date` in the returned user shape.

## Authentication implementation

- Password hashing uses the callback-based `scrypt` API through `promisify`;
  the optional `AUTH_HASH_MODE=sync` switch is for non-production lab runs only.
  The server refuses sync mode when `NODE_ENV=production`.
- Encoded password hashes carry `N`, `r`, `p`, salt, and derived key. Verify
  validates the encoding/parameters before work and uses `timingSafeEqual`
  after matching byte lengths.
- Auth handlers return only a public user projection. Unknown-email login
  verifies against a cached dummy password hash so it does comparable scrypt
  work to a wrong-password login.
- Authenticate runs before the body parser. It allows requests with no
  Authorization header through, but rejects malformed/invalid tokens even on
  public routes. `/auth/me` separately requires an authenticated user.
- Request access logs for authenticated users include both `requestId` and
  `userId`. Authorization headers longer than 8 KiB are rejected; the Node
  HTTP parser can reject much larger headers (for example 100 KiB) with 431
  before middleware runs.

HTTP tests cover public response fields, validation, duplicate emails, one
success among 20 concurrent registrations, equal login failure responses,
token forgery/expiry, absent/deleted users, public-route behavior, and
authenticated access-log fields. Password tests use `N=1024` to keep the suite
fast; production retains the default `N=16384`.

## Benchmark

Run `node bench/auth.js --http` for the default async mode, and set
`UV_THREADPOOL_SIZE` before launching Node to compare pool sizes. The script
reports hash/verify operations per second and `/health` versus `/auth/me`
throughput. The default async run measured hash/verify rates of 18.9/10.3 ops/s
at concurrency 1 and 43.4/43.1 ops/s at concurrency 4, with the default
threadpool. `/health` was 4,118 req/s and `/auth/me` was 3,376 req/s; direct
token verification measured about 20 μs/op. These are single-run observations,
not stable guarantees. Pool sizes 1/16 and sync mode are left for the Break #1
practice; see [`../bench/M4.md`](../bench/M4.md).
