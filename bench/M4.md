# M4 Benchmark - Password hashing and tokens

## Prediction before measurement

- Async `scrypt` should keep event-loop latency lower than `scryptSync`, because
  the expensive derivation runs in libuv's worker pool.
- Increasing `UV_THREADPOOL_SIZE` should improve parallel hash throughput until
  CPU/memory bandwidth becomes the bottleneck; it may delay other threadpool
  work such as filesystem operations, `dns.lookup`, and zlib.
- A token HMAC verification plus an in-memory user lookup should be much
  cheaper than one password `scrypt` verification. Password hashing belongs at
  login, not on every authenticated request.

## How to measure

The benchmark uses `N=16384`, 4 worker tasks for parallel cases, and a 3-second
measurement window. It reports password hash/verify operations per second. With
`--http`, it additionally runs autocannon at 100 connections for 10 seconds
against `/health` and authenticated `/auth/me`.

```powershell
$env:AUTH_HASH_MODE = "async"
$env:UV_THREADPOOL_SIZE = "1"
node bench/auth.js --http
```

Repeat in a new process with `UV_THREADPOOL_SIZE` set to 4 and 16. To compare
the blocking lab implementation, run with `AUTH_HASH_MODE=sync`; do not use
sync mode in production. `UV_THREADPOOL_SIZE` must be set before Node starts.

## Results

Measured once on Node.js v22.12.0 / Windows 11. `UV_THREADPOOL_SIZE` was unset,
so Node used its default pool size of 4. The benchmark uses a no-op logger sink;
results do not include writing access logs to a real stdout/log collector.
Single-run throughput has normal machine/load variance.

| Hash mode | Pool size | Hash ops/s (1 worker) | Hash ops/s (4 workers) | Verify ops/s (1 worker) | Verify ops/s (4 workers) | `/health` p99 | `/auth/me` req/s | `/auth/me` p99 | Errors |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| async | 4 (default) | 18.9 | 43.4 | 10.3 | 43.1 | 66 ms | 3,376 | 53 ms | 0 |
| async | 1 | | | | | | | | |
| async | 16 | | | | | | | | |
| sync (lab only) | n/a | | | | | | | | |

In the same run, `/health` was 4,118 req/s at p99 66 ms. `/auth/me` was about
18% lower throughput in this sample; that route adds HMAC verification, a Map
lookup, and auth middleware work. A direct `tokens.verify()` micro-measurement
reported 19,993 ns/op (about 20 μs) including HMAC-SHA256, base64 decoding,
JSON parsing, and claim validation. Password verify at concurrency 1 was about
10 ops/s (roughly 100 ms/op), thousands of times more expensive than token
verification; tokens avoid repeating scrypt on every request.

Compared with `bench/M3.md` (2,773 req/s warn and 2,715 info), these results
are not a controlled before/after: run conditions and logger sinks differ.
Repeat before drawing a performance conclusion. Remaining rows are intentionally
left blank for the hands-on threadpool/sync experiment in
[`../lab/M4-breaks-practice.md`](../lab/M4-breaks-practice.md).
