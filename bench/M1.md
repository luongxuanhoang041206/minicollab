# M1 Benchmark Baseline — GET /health

## Môi trường
| Thông số | Giá trị |
|---|---|
| **Node.js** | v22.12.0 |
| **OS** | Windows 11 |
| **Công cụ** | autocannon v8.0.0 |
| **Lệnh cơ bản** | `npx autocannon -c 100 -d 30 http://localhost:3000/health` |
| **Route** | `GET /health` → JSON 200, body 16 bytes |

---

## Thí nghiệm 1: LOG_LEVEL (access log on vs off)

| Biến | Req/s (mean) | p50 latency | p99 latency | Errors |
|---|---|---|---|---|
| `LOG_LEVEL=warn` (no access log) | **7,127** | 13 ms | 36 ms | 0 |
| `LOG_LEVEL=info` (access log bật) | **5,701** | 15 ms | 50 ms | 0 |
| **Chênh lệch** | **-20%** | +15% | +38% | — |

> **Nhận xét:** Bật access log (ghi JSON mỗi request ra stdout) tiêu tốn ~20% throughput.
> Lý do: `process.stdout.write` vẫn là synchronous write vào pipe của hệ điều hành — nếu consumer (logging agent, terminal) đọc chậm, nó sẽ block event loop.
> **Bài học:** Trong production dùng pipe sang logstash/fluentd ở process khác; hoặc dùng async transport.

---

## Thí nghiệm 2: Keep-Alive vs Connection: close

| Biến | Req/s (mean) | p50 latency | p99 latency |
|---|---|---|---|
| Keep-Alive (mặc định) | **7,127** | 13 ms | 36 ms |
| `Connection: close` | **1,590** | 62 ms | 106 ms |
| **Chênh lệch** | **-78%** | +377% | +194% |

> **Nhận xét:** Tắt Keep-Alive làm throughput giảm ~78% vì mỗi request phải thực hiện TCP 3-way handshake + 4-way teardown riêng biệt.
> Trên localhost overhead này đã rõ; trên mạng thật với RTT 20ms thì chênh lệch còn lớn hơn nhiều.
> **Bài học:** Keep-Alive là tính năng bắt buộc cho HTTP/1.1 production. Chỉ disable khi có lý do đặc biệt (e.g., load balancer layer 4 không sticky).

## Thí nghiệm 3: Concurrency (c=10 / c=100 / c=1000)

| Connections | Req/s (mean) | p50 latency | p99 latency | Errors |
|---|---|---|---|---|
| **c=10** | **5,932** | 2 ms | 3 ms | 0 |
| **c=100** | **7,127** | 13 ms | 36 ms | 0 |
| **c=1000** | **6,892** | 129 ms | 444 ms | 0 |

> **Nhận xét bất ngờ:** c=10 có req/s tương đương c=100 nhưng latency thấp hơn 6-10 lần!
> - Ở **c=10**: Mỗi connection đủ request để bão hoà server (Node.js I/O đồng thời đã đủ).
> - Ở **c=100**: Req/s cao hơn một chút (~20%), nhưng queuing delay tăng vì 100 socket tranh nhau poll phase.
> - Ở **c=1000**: Req/s giảm nhẹ, p99 nhảy vọt lên 444ms — đây là dấu hiệu scheduling overhead của OS khi quản lý 1000 TCP socket đồng thời.
>
> **Kết luận:** Server đơn giản như thế này "saturation point" vào khoảng c=50-100. Vượt ngưỡng đó, chi phí quản lý connection lấn át lợi ích concurrency.

## Quan sát bổ sung từ BREAK experiments

| Thí nghiệm | Quan sát | Số liệu chứng minh |
|---|---|---|
| `/block?ms=3000` trong khi `/health` chạy | Event Loop bị chặn hoàn toàn | `/health` mất **2796ms** thay vì <1ms; `maxMs` monitor nhảy lên **3011ms** |
| Slowloris với `headersTimeout=5000` | Server tự đóng socket sau ~5s | `clientError: Request timeout` trong log |
| `POST /echo` với `Content-Length: 2MB` | 413 trả về ngay, zero RAM consumption | Body không bao giờ được đọc |
